## Work from an issue and a branch

1. Read the task's acceptance criteria, confirm its owner, and discuss dependencies.
2. Branch from current `main` using a task name such as `research/copilot-event`, `script/presentation-draft`, or `slides/presentation`.
3. Make coherent changes with descriptive commits explaining the result. Use your own account and normal Git identity.
4. Open a pull request linking the issue. Describe the change, evidence checked, and anything still pending.
5. Have another member review the actual material and leave substantive feedback. Address comments before merging.
6. Merge through the PR and close the task with a resolving PR or commit reference only when its acceptance criteria are met.

Do not merge a PR merely to increase activity. Do not use another member's name or email to simulate their contribution.

## Review guidance

- Research: check source dates, exact claims, study conditions, and uncertainties.
- Script: verify claims against sources, flow, speaking balance, and actual rehearsal time.
- Slides: check readability, alignment with narration, attribution, and rendered appearance.
- Final video: watch all of it, check duration and audio, and test its public URL.

## Discussions

Use GitHub Discussions for topic choice, division of work, and feedback. Each member should participate in their own words. If Discussions is disabled, a repository administrator needs to enable it; an issues thread is useful but does not itself satisfy the separate Discussions rubric item.

## Stage checkpoints

The requester controls progression by saying **continue** after each stage. Keep the stage's PR available for real teammate review. Requester continuation is permission to prepare the next stage, not a claim that peer review, recording, or publication occurred.
